一页速览一 理论体系二 作品集规划三 技术栈选型

一页速览

  • 局部光照与全局光照的唯一分界：局部光照把 Li 当成常数 Ka 假装掉；全局光照承认 Li 是别处的 Lo，于是所有点被同一个方程耦合，必须联立求解。
  • 渲染方程：Lo(x,ωo) = Le(x,ωo) + ∫Ω fr(x,ωi→ωo)·Li(x,ωi)·(n·ωi) dωi。四项分别回答：自发光、材质分配、来了多少光、投影面积。
  • 三大经典模型是同一个积分的不同近似：Lambert 取常数 fr = ρ/π；Phong 用 (r·v)^p 围绕反射方向；Blinn-Phong 用 (n·h)^p 围绕半程向量，更省算力且掠射角不失真。
  • 技术选型一句话：离线求正确选路径追踪（+NEE/MIS），焦散补光子映射，实时求帧率先烘焙兜底再上 SSGI，深水区（VXGI/DDGI/PT）必须 WebGPU。
  • 作品集主线（6 个）：HDR 底座 → PBR+IBL → 阴影全家桶 → 烘焙 lightmap/SH 探针 → GTAO/SSGI → 深水区四选一。14–20 周。
  • 实现姿势：three.js 管底座与资源，光照算法全部自写 shader，另加一个小的原生 WebGL2 原理复现页作为加分项。混合路线层级一 2–3 周，全手写 5–6 周，全用内置约 5 天。

第一部分 · 理论体系

1.1 局部光照 vs 全局光照，直接光 vs 间接光

光到达着色点走了几步路，这一条变量就把两者彻底分开。

维度局部光照 Local Illumination全局光照 Global Illumination
求解对象每个着色点独立求解：只依赖该点法线、材质、光源与相机方向整个场景联立求解：任一点的颜色依赖所有其他表面
数学形式代数式求和（环境 + 漫反射 + 镜面）第二类 Fredholm 积分方程，Lo = Le + T·L 自耦合
表面角色表面只是接收者每个表面同时是接收者与光源（被照亮的墙成为面光源）
能产生的现象直接光、硬阴影、镜面高光。暗部只能靠常数环境项假装软阴影、色彩溢出、接触阴影、焦散、暗部层次
成本O(1) 每像素，可并行，天然实时高维积分，离线用蒙特卡洛，实时用缓存/近似/降噪

1.2 渲染方程与 BRDF

Lo(x, ωo) = Le(x, ωo) + ∫Ω fr(x, ωi→ωo) · Li(x, ωi) · (n·ωi) dωi

BRDF 的三条性质：非负性；亥姆霍兹互易 fr(ωi→ωo) = fr(ωo→ωi)；能量守恒（半球积分 ≤ 1）。违反任一条，渲染结果在物理上就不成立。

1.3 三种经典光照模型

模型公式几何含义优点局限
Lambertfr = ρ/π；L = kd·ρ·(n·l)余弦瓣，各方向均匀散射最省、符合理想漫反射与视角无关，无法表达任何光泽
Phongspec = ks·(r·v)^p，r 为反射方向镜面瓣围绕反射方向 r高光直观、实现简单需逐点求反射向量；掠射角处 n·l 趋于 0 时高光失真
Blinn-Phongspec = ks·(n·h)^p，h = normalize(l+v)镜面瓣围绕半程向量 h更省算力；掠射角不失真指数需 ×4 才与 Phong 视觉对齐；仍非能量守恒
三个易踩的坑：①Ka + Kd + Ks 常常 > 1，经典 Phong 本身不守恒，要物理正确应走 Cook-Torrance/GGX，或在 Ks 前加 (p+2)/(2π) 这类归一化因子；②Blinn-Phong 的指数要 ×4 才能与 Phong 对齐，否则两者混用时高光大小不一致；③p→∞ 并不等价于 GGX 的 α→0，前者是无限收窄的能量黑洞，后者仍受 Smith 遮蔽与菲涅耳约束。粗糙度与 Phong 指数的换算为 α = √(2/(p+2))。

1.6 四种视觉现象的物理与数学成因

现象数学成因关键结论
阴影渲染方程加二值可见性 V(x,ω)：Li 沿该方向能否到达取决于线段是否被挡（shadow ray）点光源下 V 非 0 即 1 → 硬阴影；面光源要对光源面积积分，部分可见产生半影，半影宽度 ≈ 遮挡物到受影面距离 × 光源张角。shadow map 只是用 depth 比较粗暴替代该积分，于是才有 acne、peter-panning、bias、cascade 这些补丁
反射理想镜面 BRDF 是狄拉克 δ：fr = ρ·δ(ωo − R(ωi))/cosθi，把积分退化成只沿一个方向真实材质用微表面模型 fr = F·D·G / (4(n·i)(n·o))；D 是法线分布（GGX）、G 是 Smith 遮蔽、F 是菲涅耳。粗糙度本质是 µm 尺度几何的统计
折射斯涅尔定律 n₁sinθ₁ = n₂sinθ₂，来自麦克斯韦方程组的界面边界条件（等价 Fermat 最小光程）；能量配比由菲涅耳决定向量形式 t = η·l + (ηc − √(1−η²(1−c²)))·n，根号内为负即全内反射，临界角 θc = arcsin(n₂/n₁)。n 随波长变化（色散）导致不同颜色折射角不同 → 彩虹与相机紫边
色彩溢出诺伊曼级数：L = Le + T·L 的解为 L = Σₖ Tᵏ·Le，第 k 项即第 k 次弹射贡献因为 ρ<1，∥T∥<1，级数几何收敛；每一项 Tᵏ 都带着上一次碰撞表面的颜色（fr 中的 ρ），红墙于是把反照率乘进后续所有项。这也解释了"每个被照亮的漫反射表面都是一个面光源"

2.3 Web 端可行性红线

WebGL2 没有 compute shader

体素化、探针更新、SVGF 降噪、BVH 重建等高频并行任务，在 WebGL2 下只能用多 pass 片元着色器或 CPU 兜底。VXGI / DDGI / 实时 PT 应直接上 WebGPU。

Web 端没有硬件光线追踪

不存在 DXR / Vulkan RT 的等价物。所有"路径追踪"都是 GPU compute 软件光追 + BVH，必须靠累积或离线烘焙。宣传措辞要准确。

3D 纹理可用但代价不同

WebGL2 支持 TEXTURE_3D，但采样开销与显存更敏感；辐照度体积、froxel 雾、SDF 都能做，分辨率要保守（64³–128³）。

移动端瓶颈在带宽而非算力

ray march 半分辨率起步、MRT 控制在 2–3 张、后处理 pass 合并、KTX2/Basis 与 ASTC 压缩、DPR 上限设 2；移动端档位默认回落到烘焙方案。

WebGPU 覆盖要实测

桌面 Chrome/Edge 与多数 Android 已可用，iOS 与旧设备需逐版本核验。每个 WebGPU demo 都应配 WebGL2 或烘焙结果的降级路径并显式标注。

精度与噪声

WebGL2 需核对浮点渲染目标与线性过滤扩展；半精度累积会引入条带。TAA/累积类算法建议优先 WebGPU，并用抖动 + 蓝噪声缓解。

2.4 每个 Demo 必备的八块内容

  1. 一句话问题陈述——解决什么、为什么难，两行以内。
  2. 算法概要——3–5 句 + 关键公式，说明输入、输出与核心假设。
  3. 实时画布——可全屏，至少 2 个预设视角 + 自动巡航；鼠标/触控/键盘均可用。
  4. 交互控制面板——滑块 + 开关 + 预设；状态序列化进 URL query，可直接分享复现。
  5. 中间量可视化——G-buffer、cascade 分层、探针图集、SDF 切片、方差图做成下拉项。这是最能体现"我真的做了"的部分。
  6. 性能面板——帧时间、各 pass 耗时分解、draw call、显存、当前分辨率与质量档位。
  7. 局限与已知问题——诚实列出失效案例（屏幕外信息缺失、漏光、时域拖影）。
  8. 源码与参考——核心 shader 片段、论文/博客出处、资产来源。

首页卡片：3–5 秒循环 GIF 封面（展示参数变化过程）+ 标题 + 一句话陈述 + 三个标签（层级/栈/实时或烘焙）+ 一个关键指标（如「1 spp 起始 · 收敛至 512 spp · 桌面 60 FPS」）。

2.5 工程加分项

性能剖析与自适应

GPU 计时（EXT_disjoint_timer_query_webgl2 / WebGPU timestamp-query）；帧时间反馈控制分辨率与质量档；长帧归因到具体 pass。

多级降级路径

WebGPU → WebGL2 → 烘焙静态结果 → 预渲染视频。每级明确"损失什么"并显式标注当前档位。

资产流水线脚本化

GLTF + Draco/meshopt、KTX2/Basis、HDR → PMREM；烘焙器做成 Node CLI，产物入库、可复现、有版本号。

视觉回归与性能门禁

Playwright 截图对比 + 固定 seed 的确定性随机 + FPS 阈值断言，接入 CI。

共享基础设施

monorepo 拆分 demo，共用 HUD/控制面板/性能采集；shader 变体管理与编译缓存；统一相机与场景加载器。

移动端与无障碍

触控相机、DPR 上限、帧率上限、内存预算；键盘可达的参数面板、aria 标注、尊重 prefers-reduced-motion。

3.1 结论与成本对比

结论：混合实现。three.js 负责底座与资源，光照算法全部自己写 shader，另加一个体量很小的原生 WebGL2 原理复现页作为加分项。不建议从零手写整条管线，也不建议全用内置材质。

3.2 职责划分

3.3 自写 shader 的四种落地手段

  1. ShaderMaterial / RawShaderMaterial——完全自己写 vs/fs 与 uniforms。适合独立算法页（BRDF 球、SSR、SSGI 后处理 pass）。代价：不享受 three 的灯光/阴影/雾自动注入，相机矩阵与光源数据要自己传。
  2. onBeforeCompile + chunk 替换——侵入内置材质，替换 lights_fragment_begin、shadowmap_pars_fragment 等 chunk。适合在保留 three 场景图与灯光系统的前提下换掉 BRDF 或阴影采样（PCSS 通常这么做）。代价：依赖 three 内部 chunk 命名，版本升级易碎。
  3. TSL / NodeMaterial（three.js WebGPU 路线）——节点图写 BRDF，同一份代码可编译到 WebGL2 与 WebGPU 两个后端。适合已确定深水区要用 compute（DDGI / VXGI / PT）时的长期选择。代价：生态仍在演进，调试不便。
  4. 自建 pass（推荐的主姿势）——three.js 只当"场景 + 资源 + GL 状态"管理器，渲染流程自己组织：WebGLRenderTarget 手写 G-buffer（MRT）、自己写 deferred light pass、自己组织后处理链（全屏 quad + 手动 setRenderTarget 循环）。完全控制管线，又不必重写矩阵、加载器与纹理解码。多光源剔除、deferred、SSGI、降噪都应在这种姿势下做。

3.4 层级一逐项落地方式

3.5 R3F 还是 vanilla three

页面多、需要路由与参数面板，React 管 UI 是合理的；但渲染侧建议封装成 vanilla three 的 class/模块，React 只负责挂载与 UI。原因是作品集多数 demo 需要顺序敏感的自建多 pass 管线，R3F 的 reconciler 与自定义 composer 容易打架。折中：简单页（材质球、IBL 展示）用 R3F，复杂多 pass 页用 vanilla。

3.6 什么时候真的该手写原生 WebGL2

  • 证明底层掌控力：做一个"原理复现"小页，手写 shadow map 或最小 deferred，400–600 行、单文件、零依赖，附源码。性价比很高，但不该成为主 demo 的实现方式。
  • 需要完全控制 GL 状态与扩展：timer query、texture array、MRT、UBO 这些地方，three 的抽象反而碍事，原生更直接。

3.7 三个风险提示

  1. onBeforeCompile 依赖 three 内部 chunk 命名——必须锁版本、集中管理注入点、加冒烟测试。
  2. three.js 的重心正在迁向 WebGPURenderer / TSL，WebGLRenderer 未来进入维护状态。若深水区要用 compute，建议直接选 WebGPU 后端，避免出现"WebGL2 版 + WebGPU 版两套代码"。
  3. 性能归因不要只看 renderer.info——它不提供 GPU 时间。用 EXT_disjoint_timer_query_webgl2（WebGPU 用 timestamp-query）自己测每个 pass。

替代框架：Babylon.js 内置能力最全（SSAO/SSR/体积光/HDR/IBL 都有，WebGPU 支持成熟），适合"要开箱效果"的路线，代价是自写 shader 自由度与社区示例不如 three、React 集成偏弱。若目标是展示"我实现了算法"，three 仍是更合适的地基。
